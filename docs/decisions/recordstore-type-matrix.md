# RecordStore and DuckDB logical-type compatibility matrix

Status: accepted (Phase 0 deliverable, PRD §9.4, §10.1, §11)

## Context

ixtable writes records to SQLite or PostgreSQL through a `RecordStore` and reads
every record through DuckDB (`sqlite_scanner` or `postgres_scanner`, both
checksum-pinned v1.5.5). A designer column has a *logical* type. Each store maps
it to a physical type, and the reader converts what DuckDB returns back into one
canonical value, so the same record reads the same on either store.

## Decision

| Logical type | SQLite declared type (+ enforcement) | PostgreSQL type | DuckDB type over SQLite | DuckDB type over PostgreSQL | Canonical value (`DataValue`) |
|---|---|---|---|---|---|
| `text` | `TEXT` | `TEXT` | VARCHAR | VARCHAR | `text` |
| `integer` | `INTEGER` | `BIGINT` | BIGINT | BIGINT | `integer` (i64) |
| `real` | `REAL` | `DOUBLE PRECISION` | DOUBLE | DOUBLE | `real` (f64) |
| `decimal(p,s)` | `DECIMAL(p,s)` + CHECK `typeof IN ('integer','real')`, p ≤ 15 | `NUMERIC(p,s)`, p ≤ 38 | DOUBLE | DECIMAL(p,s) | `decimal`, plain notation with exactly `s` fraction digits (`"12.30"`) |
| `boolean` | `BOOLEAN` + CHECK `IN (0,1)` | `BOOLEAN` | BIGINT | BOOLEAN | `boolean` |
| `date` | `DATE` + CHECK `date(c) IS c` | `DATE` | DATE | DATE | `date`, `YYYY-MM-DD` |
| `time` | `TIME TEXT` + CHECK `time(c) IS NOT NULL` | `TIME` | VARCHAR | TIME | `time`, `HH:MM:SS[.ffffff]` (trailing zeros trimmed) |
| `timestamp` | `TIMESTAMP` + CHECK `datetime(c) IS NOT NULL` | `TIMESTAMP` | TIMESTAMP | TIMESTAMP | `timestamp`, `YYYY-MM-DDTHH:MM:SS[.ffffff]`, UTC, no zone |
| `uuid` | `UUID` + CHECK text of length 36 | `UUID` | VARCHAR | UUID (read as VARCHAR) | `text`, lower-case hyphenated |
| `json` | `JSON` + CHECK `json_valid(c)` | `JSONB` | VARCHAR | JSON (read as VARCHAR) | `text` (PostgreSQL re-serialises JSONB) |
| `blob` | `BLOB` | `BYTEA` | BLOB | BLOB | `blob`, base64 |

`NULL` is `{"type":"null"}` for every type on both stores.

The SQLite CHECK constraints are named `ixt_type_<column>`. The DDL parser
drops them from the user-visible definition, and a table rebuild regenerates
them for the new type.

## Rules that make values equal across stores

- **Writes are normalised first.** `LogicalType::normalize` validates and
  canonicalises every value before either store sees it. Text input is accepted
  for every type, so a grid can send what the user typed. A decimal with more
  fraction digits than its scale is rejected: PostgreSQL would round it and
  SQLite would keep it, so neither behaviour is safe to rely on.
- **Reads are coerced last.** `LogicalType::coerce_read` turns what DuckDB
  returns into the canonical form: BIGINT 0/1 becomes boolean, DOUBLE becomes a
  decimal with the column's scale, and text dates and times are re-formatted.
  `duck_value` converts DuckDB DECIMAL, DATE, TIME, TIMESTAMP, HUGEINT, and
  nested values losslessly instead of using `Debug` text.
- **Timestamps are UTC without a zone.** RFC 3339 input with an offset is
  converted to UTC on write.
- **Parameters are always bound.** SQLite binds typed `?` values; PostgreSQL
  binds text `$n` parameters cast to the catalog type
  (`$1::text::numeric(10,2)`, `decode($1,'base64')` for bytea).

## Differences that stay visible

These are published in `StoreCapabilities` and shown in Settings › Datasource,
not emulated:

- SQLite decimals are limited to 15 digits of precision (NUMERIC affinity keeps
  a 64-bit float). The designer caps precision at the store's `maxPrecision`.
- SQLite needs a table rebuild for type, nullability, key, unique, check, and
  foreign-key changes; PostgreSQL changes them in place. The designer labels
  each staged change "Changes in place" or "Requires table rebuild" from the
  store's own preview.
- DuckDB's `sqlite_scanner` does not read SQLite generated columns. They appear
  in the designer but not in record pages.
- Tables without a primary key are editable on SQLite (rowid identity) but not
  on PostgreSQL.
- A single `integer` primary key auto-generates on both stores: SQLite through
  the rowid alias, PostgreSQL through `GENERATED BY DEFAULT AS IDENTITY`.

## Proof

`src-tauri/src/recordstore/conformance.rs` and `conformance_more.rs` run the
same scenarios against both stores and read every result through DuckDB.
`conformance.rs` covers CRUD and read-after-write, constraint error codes and
cascades, atomic batches and parameter binding, and the type round-trip above
(including nulls). `conformance_more.rs` covers optimistic conflicts, schema
changes, and migrations.

```bash
cd src-tauri
cargo test --lib recordstore::                                   # SQLite only
IXTABLE_TEST_POSTGRES_URL=postgres://postgres@127.0.0.1:54329/ixtable_test \
  cargo test --lib recordstore::conformance                       # both stores
```

Without `IXTABLE_TEST_POSTGRES_URL`, PostgreSQL scenarios are skipped with a
message. The scanner extensions resolve DuckDB symbols from the shared
prebuilt libduckdb (see `duckdb-read-path.md`).
